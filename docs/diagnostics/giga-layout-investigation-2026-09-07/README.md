# GIGA Android：複数回レイアウトと Taffy キャッシュの調査

2026-09-07。対象は `7d76eed8` の性能改善後の debug ビルド。製品コードは変更せず、一時的な依存差し替えによる測定と原因切り分けだけを行った。

## 結論

レイアウト負荷には、独立した二つの増幅要因がある。

1. Taffy のサイズ計算キャッシュから結果が上書きされ、同じ部分木のサイズ計算が繰り返される。キャッシュ保持方法だけを変えた実験では、Reader 復帰の4パス合計のキャッシュミスが **6,259 → 562**、約91%減った。2回とも同じ件数だった。
2. Whisker の文字計測キャッシュが Android の Text provider が使わない `available_space.height` まで区別している。ここだけをまとめた実験では、Reader 復帰の Host 計測要求が **29 → 8**、レイアウトが **4 → 3パス**になった。これも2回で一致した。

したがって、Taffy の呼び出し内が重いことと、レイアウト計算そのものが不可避に重いことは区別する必要がある。まず再利用できる計算結果の破棄を減らし、次に Host 計測の同値な条件をまとめる方針が妥当。

## 方法と限界

- Android emulator-5554、API 37、1080×2400。実機・release ビルドでの測定ではない。
- 前回と同じ GIGA の Home → キングダム → Reader → Group → 一覧6スワイプ → Home を実行。各操作は7秒、スクロールは10秒記録。
- 元の実装、Text の高さキー正規化だけ、Taffy のキャッシュ保持変更だけ、の3種類を各2周。変更を重ねず、原因を別々に検証した。
- Perfetto の既存区間に加え、Taffy root 計算、snapshot 収集、copy-on-write の時間、キャッシュ hit/miss、ユニークな計算対象ノード数、dirty ノード数、Host 計測条件・要求数を記録。
- カウンターはパス単位で集約。テキスト本文は記録せず、ノードID・内容とスタイルのハッシュ・制約のみ記録した。
- `passes.csv` は実際に計算したパスの全件。`chains.csv` は要求がなくなるまでの連続パスをまとめたもの。元のトレースでも、Reader 復帰の該当4パスは同一 tick 内で実行されている。
- 計測自体にコストがある。特にキャッシュ参照ごとのカウンターと集合への挿入、パス終了後のファイル出力が加わるため、時間は製品ビルドの性能保証ではない。比較の強い根拠は2回で一致した仕事量の差。
- CPU 内訳には前回の simpleperf 結果も使用した。今回の実験 APK で新たな CPU サンプリングは行っていない。

## 4パスになる理由

Reader 復帰では、同じ1つの Text ノードの計測条件が次の順に増える。

| パス | 新しい Host 計測要求 | Taffy キャッシュミス | 計算開始前の dirty ノード | 主な状態 |
| --- | ---: | ---: | ---: | --- |
| 1 | 13 | 3,994 | 32 | intrinsic min/max、幅0、幅323.43、仮の高さ16など |
| 2 | 12 | 1,237 | 14 | 回答により幅50.29・13.71、高さ19.81などが判明 |
| 3 | 4 | 744 | 14 | 判明した幅と高さの組み合わせを再要求 |
| 4 | 0 | 284 | 14 | 要求がなくなり確定 |

全体は499 retained ノード。2回とも、要求数・miss 数・dirty 数が同じだった。`Block` の未計測サイズは0で、その回答を取得した後に Flex の制約が変わり、新しいキーが必要になる。`13.714286` と `13.714287` のような僅かな幅の違いも別キーとして観測された。これを根拠なく丸める修正は提案しない。

スクロールでは新しく表示するテキストごとに同じ13→12→4の系列が生じた。例として4つの新しい Text を含む更新では、52→48→16→0件となった。

全ノードのキャッシュを毎回消しているわけではない。2パス目以降に記録された measurement invalidation は同じ1ノードで、その祖先まで dirty になる。途中パスで style/children の再変更や unresolved request の再無効化は観測されなかった。それでも、2パス目には152ノードで1,237回の miss が起こる。dirty ノード数だけでは計算量を説明できない。

関連実装：

- `crates/whisker-engine/src/layout.rs` の `drive_layout`：計算→Host一括計測→応答反映を繰り返す。
- `crates/whisker-engine/src/measurement.rs` の `cache_key` / `use_fallback`：制約全体をキーにし、Block の未計測値を0とする。
- `crates/whisker-engine/src/surface.rs` の `compute_layout_with_measurements` / `apply_measurement_responses`：計測対象と祖先の再計算。

## 独立した二つの実験

Reader 復帰の同じ4パス系列を比較する。時間は Taffy root の計算全体で、Rust 側の計測キャッシュ参照を含む。Host の FFI 実計測は含まない。

| 条件 | Host要求の系列 | パス別 Taffy miss | Taffy root 合計：1 / 2周目 |
| --- | --- | --- | --- |
| 元の実装 | 13 / 12 / 4 / 0 | 3,994 / 1,237 / 744 / 284 | 114.8 / 151.8ms |
| Textのavailable heightだけ正規化 | 5 / 3 / 0 | 3,994 / 1,236 / 744 | 78.4 / 164.1ms |
| Taffyのサイズキャッシュ保持だけ変更 | 13 / 12 / 4 / 0 | 205 / 146 / 106 / 105 | 18.3 / 33.5ms |

### Text のキー

Android の `platforms/android/runtime/src/main/kotlin/rs/whisker/runtime/measure/TextMeasurement.kt` は、Text の計測本体に available height を渡していない。一方、known height は戻り値に使用するため除去しなかった。Text 以外も変更していない。

この実験は Android の現在の provider に限った根拠である。汎用の計測キャッシュで全種類・全 Host の高さを無条件に無視する仕様にはしない。製品化では、Text 計測の契約と他 Host の実装を確認し、同じ結果を保証できる条件を明示する。

### Taffy のキーと保持

使用バージョンは Taffy 0.13.0。`src/tree/cache.rs` は最終レイアウト用1枠とサイズ計算用9枠を持つ。サイズ計算の保存先は known dimensions の有無と min/max の分類で決まり、同じ分類の別制約が以前の結果を上書きする。

実験ではサイズ計算側だけを、無効化されるまで異なるキーを保持するベクターに置き換えた。最終レイアウト用のキャッシュと計測キーはそのまま。大幅な miss 減少は、既存の枠への上書きがこのワークロードの再計算を増やしている証拠となる。

ただし無制限の保持であり、製品にそのまま採用できない。メモリー使用量、キャッシュ検索、スナップショット複製費用を検証していない。また Group 初期表示では計測要求が一部変化した（あるパスが131→135件）。全レイアウトの厳密同値性の試験は未実施。実験 APK は原因切り分け専用。

## Taffy と周辺処理の割合

前回の固定版スクロールの simpleperf（UIスレッド1,822サンプル）では、`LayoutTree::compute` が44.46%、Taffy呼び出し内が40.12%、snapshot収集が4.34%。Taffy呼び出し内にはRust計測コールバックの7.35%も含まれる。包含関係がある数値を合計しない。

今回の元実装 Reader 復帰1周目では、該当4パスの Taffy root は114.8ms、snapshot収集は約7.0ms、compute直前の copy-on-write は合計0.01ms未満だった。Taffy呼び出し内が主で、snapshotも全ノードを毎回収集するが、今回の最優先ではない。Taffy のピクセル丸めは Whisker 側で無効化されており、この測定には丸め処理の時間はない。

## 推奨する次の実装作業

1. **サイズ計算の再利用を改善する。** 今回の制約系列を最小再現に落とし、同じ幾何結果を保てることをテストする。メモリー上限・破棄タイミング・更新時の無効化を定め、Taffy 側のキャッシュ改善と Whisker の計算中メモ化を比較する。GIGA の画面固有の例外を入れない。
2. **Text の計測キーを実際の依存条件に合わせる。** Host ごとの契約を確認し、known height、改行、最大行数、書体・DPI・環境 epoch を壊さず、同値な要求を共有する。
3. **製品版の計測で評価する。** 計測コードなしで同じ操作の frame time を反復比較し、メモリー増加や COW の費用を含める。今回の実験だけで16ms以内やフレーム落ち解消は宣言しない。
