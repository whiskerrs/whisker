# GIGA Android：共有スナップショットと部分木削除の最適化

2026-09-07。[前回の詳細プロファイル](../giga-detailed-profile-2026-09-07/README.md)を元に Whisker の共通処理を変更した。GIGA の画面別の例外や、計算結果を不完全なまま表示する処理は追加していない。

## 変更した責務

- `SurfaceEngine` の複製では、レイアウト、計測状態、直前のレイアウト結果、変換・背景情報を共有する。更新対象の状態だけを copy-on-write で独立させる。既存の speculative snapshot によるロールバック契約を保つ。
- `Scene` はノード単位で未変更データを共有する。あるノードの描画属性を変えても、兄弟ノードのテキスト・属性・描画データを複製しない。ノード索引自体の複製は残る。
- `MeasurementCoordinator` は計測応答を全件検証した後、対象の要求・キャッシュだけに反映する。キャッシュ全体を複製してから書き込む方式を廃止した。同一バッチ内の重複キー、古い epoch、重複 pending ID の扱いと、エラー時の原子性を維持する。
- Android の `SceneTopology` が親と子の関係を一元管理する。事前検証と実際の削除が同じ木構造を利用し、削除は対象の部分木だけを辿る。構造を変更しないフレームの検証では木の複製も不要になる。検証用の木は実画面の木から独立しており、失敗したフレームは反映しない。破棄は子から親へ進める。

スナップショットが生存している間は古いデータも保持する。レイアウトや計測そのものを変える場合には、その状態を初めて変更するときの複製が必要になる。そのため `style.clone` の時間だけでなく、`style.apply` 全体も比較する。

`SurfaceEngine` はもともと `LayoutTree` の制約でスレッドをまたいで共有できないため、内部状態には `Rc` を使う。独立して利用できる `Scene` のノード共有には `Arc` を使う。アプリ向けコンポーネント API は変更していない。低水準の `SurfaceEngine::layout_tree` と `last_layout` は参照先の共有化により `const fn` から通常の `fn` になる。`LayoutTree` に retained style / measurable 状態の読み取りメソッドを追加した。

## 比較方法

- 同じ `emulator-5554`（API 37、1080×2400）、同じ GIGA データ、Rust debug ビルドで比較する。
- baseline は前回の詳細プロファイルで作成した APK（既存の runtime 最適化あり）。fixed は今回の engine / layout / runtime とローカル Android SDK を組み込んだ APK。
- APK を入れ替えてプロセスを起動し、Home のキングダム → 第885話の続きを読む → Back → 一覧を6回スワイプ → Back、の順序を繰り返す。
- Perfetto は各 APK で2周。別途、プロファイラーを停止した対照測定と、修正版の simpleperf CPU サンプリングを実施する。処理区間は前回と同じ。
- 新旧を比較する測定中はビルド・テスト・トレース解析を同時実行しない。各操作で PID の維持と描画フレームの発生を検査し、操作前後の画像を保存する。
- `warmup` と名付けた先行測定は実装途中の共有方式による試走であり、最終版の比較から除外する。

アプリデータの削除やログアウトは行わない。計測用の依存差し替えは GIGA の manifest / lockfile に残さない。計測用 APK とトレースは `/tmp/giga-shared-state-profile` に保存する。


## 測定結果

### UI 更新とスナップショット複製

UI 更新は Android から Rust に入って戻るまでの `driver.tick`。同期的な Host 処理も含み、表示フレーム全体とは異なる。括弧内は各周の値で、最良値だけを選んだ比較ではない。

| 操作 | 最長 tick：前 → 後（ms、1 / 2周目） | コピー平均：前 → 後（ms、1 / 2周目） |
| --- | --- | --- |
| Group表示 | 714.2 / 169.2 → 632.1 / 741.0 | 5.64 / 1.78 → 0.25 / 0.30 |
| Reader表示 | 215.9 / 50.0 → 116.3 / 173.7 | 7.97 / 2.32 → 0.37 / 0.76 |
| Reader→Group | 231.5 / 17.7 → 117.6 / 188.8 | 11.44 / 1.70 → 0.21 / 0.38 |
| 一覧スクロール | 252.4 / 39.6 → 177.0 / 221.4 | 8.26 / 2.00 → 0.36 / 0.53 |
| Group→Home | 117.9 / 34.7 → 56.7 / 90.1 | 10.92 / 2.74 → 0.24 / 0.47 |

全10組で複製区間は短縮した。ただし copy-on-write の初回変更費用を含むスタイル反映全体や画面全体が、全測定で短縮したわけではない。完全な数値は [perfetto.csv](perfetto.csv) に記録した。特に baseline 2周目はレイアウト時間も大幅に短く、今回の変更だけでは説明できない大きな測定間変動がある。

### CPU サンプリング

UI スレッドの CPU-clock サンプルのうち対象関数がスタックに含まれた割合。関数間には重複があるため合計しない。

| 操作・処理 | 前 | 後 |
| --- | ---: | ---: |
| スクロール：SurfaceEngine 複製 | 7.51% | 0.38% |
| スクロール：計測応答反映 | 6.77% | 0.60% |
| Home復帰：Android フレーム検証 | 13.78% | 2.78% |
| Home復帰：Android ノード削除 | 8.44% | 1.11% |

スクロールのサンプル数は前1,905・後1,822、Home復帰は前225・後180。少ないサンプルからの厳密な時間比は算出しない。Reader表示は前33・後204フレームで、画像到着後の更新などを含む仕事量が揃っていない。サンプル CPU 時間の総量を、そのまま実装の高速化率とは扱わない。[cpu.csv](cpu.csv) に件数と割合を記録した。

### プロファイラー停止中の対照

同じ計測用 APK で Perfetto / simpleperf を停止した1周の `dumpsys gfxinfo`。区間プローブはバイナリ内に残るが ATrace は無効。これは1回の観測であり、統計的な回帰判定ではない。

| 操作 | p95 前 | p95 後 |
| --- | ---: | ---: |
| Group表示 | 101ms | 48ms |
| Reader表示 | 65ms | 105ms |
| Reader→Group | 34ms | 36ms |
| 一覧スクロール | 48ms | 48ms |
| Group→Home | 38ms | 34ms |

Group表示の短縮だけをもって全体の改善とは判定しない。Reader表示はこの測定では悪化し、スクロールの p95 は同じだった。全体の安定化と16ms以内の実行は未達。[controls.csv](controls.csv) にはフレーム数・jank率も保存した。


### Reader 表示の追加反復

対照の Reader 表示が 65→105ms だったため、同じ章を一度開いて画像を読み込ませた後、Reader の表示と復帰を各6回繰り返した。修正版は計測コードを外した APK、baseline は ATrace 無効の旧計測 APK。各操作の記録区間は2.5秒。

| 操作 | 各回p95の中央値：前 | 後 | 各回p95の範囲：前 | 後 |
| --- | ---: | ---: | --- | --- |
| Reader表示 | 150ms | 150ms | 150–250ms | 133–150ms |
| Reader→Group | 150ms | 141.5ms | 101–150ms | 81–200ms |

Reader表示の一貫した悪化は確認できなかったが、高速化の根拠にもならない。各回の p95 の中央値であり、全フレームを合算した p95 ではない。[reader-repeats.csv](reader-repeats.csv) に全測定を保存した。

## 残る負荷と判断

今回の変更は、正しさを保ったまま「変更しない状態の複製」と「削除対象以外の探索」を減らす。コピーを初回書き込みへ移す費用もあるため、複製時間だけを全体の改善率として扱わない。CPU サンプル上でも計測応答・削除の負荷低下を確認できたため、この共通処理の改善は維持する。

一方でフレーム落ちの解消は未達。修正版スクロールの CPU サンプルでは `LayoutTree::compute` が約44.5%を占め、遅い更新では依然として文字計測を挟んだ複数回のレイアウトが走る。次に調べる対象はレイアウトキャッシュの無効化範囲と、計測制約が変わって再計算が必要になる過程。正しい寸法を取得する前に表示したり、計算回数に上限を設けて処理を打ち切ったりする回避策は入れない。
