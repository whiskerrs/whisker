# ゲームエンジンの共通機能を slime 基準で仕分ける

ゲームエンジンの一般的な機能は、**描画、streaming / LOD、asset pipeline、game loop、entity model、入力、camera、animation、物理・衝突、particle / VFX、音声、UI / text、scripting、AI / navigation、networking、save、editor / tools、platform 対応**の 18 領域にほぼ収まります(分類は本調査の整理で、権威ある標準はありません)。Unreal Engine と Unity はほぼ全領域を標準機能か公式 package で持つ上限、Flame は core と bridge package で最小構成を示す下限です。Godot は editor 込みの統合型、Bevy は physics や navigation などを第三者 crate に任せる狭い本体型です。一方、slime が実際に使うのは偏った一部です。**描画、streaming、offline の asset 変換は厚く、物理エンジン、ECS、navmesh、ネットワーク同期、save、editor はありません**。音声、HUD、text、入力の一部、gzip 展開はブラウザに任せています。したがって slime 同規模の要件で最初に問われるのは、機能の網羅性より 3D 描画と大量データの扱いです。最大の不確実性はモバイルです。**slime にはモバイル実機の fps、メモリ、発熱の計測がなく、性能記録はほぼ M4 Mac のものです**。「モバイルで slime 規模が成立するか」は本調査では判定できません。

## 18 領域のうち slime が厚いのは描画周辺に限られる

次の表は本調査の 5 本のノートを統合したものです。凡例は ◎=本体または公式 package で確認、△=部分的または実験的、外=第三者または外部ライブラリの bridge、未検証=一般には存在するとされるが本調査で出典を取れていない項目、—=確認できなかった項目(不在の断定ではありません)です。Flame の「2D」は 2D 専用の機能であることを示し、3D 基準では評価しません。版は UE 5.8、Unity 6(6000.6 が Current、LTS は 6.3)、Godot 4.7、Bevy 0.20、Flame 1.38 です。

| 領域 | UE 5.8 | Unity 6 | Godot 4.7 | Bevy 0.20 | Flame 1.38 | slime が実装しているもの |

| 描画 | ◎ Nanite、Lumen、MegaLights | ◎ URP / HDRP | ◎ 3 renderer | ◎ wgpu | 2D(Flutter Canvas)。3D は △ flame_3d | **厚い**: wgpu 上の deferred、GPU 駆動 culling、TAA、PCSS |

slime の記述の根拠は、調査対象 HEAD `7383a5e`(chantoinc/slime)に対する 3 区分で示します。【コード】はソースで確認、【実測】はファイルやデータを数えた値、【文書】はリポジトリの文書にのみ記載があり再計測していない値です。**性能値はすべて【文書】**で、一部は前身プロジェクト openworld の記録であり、現在の佐世保ワールドの値ではありません。slime はコード流用の対象ではなく、必要な規模を測る物差しとして扱います。

規模の実測は次のとおりです。ランタイムは Rust 27,678 行 + WGSL 5,543 行 + HTML/JS 805 行、全体で Rust 36,095 行です。配布データは 476MB、5,654 ファイルで、gzip 後は 185MB です(うち地形が約 192MB で最大)。配置 instance は **7,409 個**で、文書の「約 9000 個」とは一致しません。HLOD の箱は 13,591 個、主人公は 30,782 三角形 24 関節、ボスは 41,343 三角形 19 関節、描画パイプライン生成の呼び出しは 33 か所です(いずれも【実測】)。調査ノートが提案する基準案は、8km 四方の streaming world、配置 7〜8 千、3〜4 万三角形のキャラクター、skin 付き群衆数百、同時 particle 2〜3 千、パイプライン 30 超、配布データ 200MB 級です。これは調査者の推論で、particle の実数は未計測です。判明しているのは上限だけです。

エンジンの輪郭には定義がありません。Gregory の教科書は第 4 版で runtime と tools / asset pipeline を別の節に分け、基盤から gameplay へ積み上げる章構成を取ります([目次](https://www.gameenginebook.com/toc.html))。ただし公式な層の定義は本調査で確認できず、全体の層図も未検証です。次の 4 段階は事例から組み立てた**本調査の作業定義**で、出典のある分類ではありません。

| 層 | 内容 | 事例 |
|---|---|---|
| L0 描画ライブラリ | 描画 API、任意で scene graph と loader | react-native-skia、three.js |
| L1 loop フレームワーク | 更新 loop と entity 管理のみ | react-native-game-engine |
| L2 最小エンジン | loop、object lifecycle、sprite / animation、衝突判定、入力の振り分け、camera、pause、asset 読み込み、音声への導線 | Flame core + flame_audio |
| L3 統合エンジン | 物理統合、editor、asset pipeline、配布 | Defold、Cocos Creator、Godot、Unity、Unreal |

この尺度で見ると、slime は変則的です。editor も物理もない一方、描画と asset 変換の水準は多くの 2D L2 を大きく超えます。Flame のような 2D の下限を満たしても slime 規模には届きません。

## 描画、streaming、asset 変換が slime 規模の中心になる

### 描画: 画面を作る処理

描画は 3D データから毎フレーム画像を作る領域です。forward は物体ごとに全光源を計算し、deferred は先に表面情報を G-buffer に書いて光を一度だけ計算します。deferred は多光源に強い一方、メモリ、半透明、MSAA に弱みがあります([LearnOpenGL](https://learnopengl.com/Advanced-Lighting/Deferred-Shading))。culling は見えない物の除外、instancing は同じ物の一括描画です([Frustum Culling](https://learnopengl.com/Guest-Articles/2021/Scene/Frustum-Culling)、[Instancing](https://learnopengl.com/Advanced-OpenGL/Instancing))。

上限の機能はモバイルに直結しません。**Nanite(必要な細部だけを処理する仮想化 geometry)の対象はコンソールとデスクトップ**です([Nanite](https://dev.epicgames.com/documentation/en-us/unreal-engine/nanite-virtualized-geometry-in-unreal-engine))。Lumen(実時間の間接光)の Android に関する記述は、ノートでは文意が曖昧で未確認です。UE 5.8 ではモバイルの既定が deferred になりました([5.8 notes](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-5-8-release-notes))。Unity は URP を全 platform 向けに前進させ、HDRP は iOS と Android に非対応です([戦略](https://unity.com/topics/render-pipelines-strategy-for-2026)、[機能比較](https://docs.unity3d.com/6000.6/Documentation/Manual/render-pipelines-feature-comparison.html))。Godot は Forward+、Mobile、Compatibility の 3 段で、**VoxelGI、SDFGI、SSIL、volumetric fog、SSR、SSS、TAA、FSR2 は Forward+ 限定、compute shader は Compatibility で使えません**([Renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html))。Bevy は wgpu 30 に乗り、0.19 で render graph を ECS schedule に置き換えました([Cargo.toml](https://raw.githubusercontent.com/bevyengine/bevy/v0.20.0/crates/bevy_render/Cargo.toml)、[0.19](https://bevy.org/news/bevy-0-19/))。GPU 駆動描画の完全対応は Windows / Linux の Vulkan のみという記述がありますが、0.16 時点の古い情報です([0.16](https://bevy.org/news/bevy-0-16/))。Flame の 2D は Flutter Canvas に描き、flame_3d は「production で使わないで」と明記します([flame_3d](https://pub.dev/packages/flame_3d))。

slime が要求するのは、2 段階の occlusion culling と間接描画(【コード】`crates/renderer/src/cull.rs`、`hiz.rs`)、G-buffer ベースの deferred(【文書】`docs/ENGINE_HISTORY.md`、実装は【コード】`gbuffer.rs`)、3 段カスケードの影、TAA、GTAO、SSR、画面空間 GI、大気 LUT、屈折する半透明のスライム本体です。動的解像度 0.5〜1.0 と品質段階も持ちます(【コード】`crates/game/src/resolution.rs`、`quality.rs`)。依存は wgpu のみで、**GLES と WebGL は明示的に除外**しています(【コード】`crates/renderer/src/lib.rs`)。

ここに本調査で最も重い論点があります。slime の TAA、SSR、ボリュメトリック光は、Godot が Forward+ 限定とする機能と名前が重なります。つまり **slime の画質セットは、少なくとも Godot の Mobile tier の範囲を超えています**(機能名の照合による筆者の解釈で、実装の同等性は未確認です)。モバイル GPU は tile ベースが一般的で、メモリ帯域が支配的な性能要因です([Vulkan Guide](https://docs.vulkan.org/guide/latest/tile_based_rendering_best_practices.html))。Apple は deferred shading と TBDR を別物と明記し、G-buffer の書き戻しは帯域を食うものの tile 内に収めれば中間 texture を省けるとします([Apple](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering.md))。slime の構成がそのまま持ち込めるかは、slime 側に実測がなく未確定です。M4 Mac でも、森の景色の 2858x1764 内部解像度 1 で High 43ms、Medium 25ms、Low 13ms です(【文書】`ENGINE_HISTORY.md`)。

### Streaming / LOD: 必要な範囲だけを読む

streaming は広い世界を分割して必要な部分だけ読む仕組み、LOD は遠くの物を低詳細に替える仕組みです。HLOD は複数の物をまとめて替えます。Unreal の World Partition はグリッドセルを streaming source からの距離で読み込みます([World Partition](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine))。Unity は Addressables を持ち、6.6 で Web の Progressive Asset Loading を追加しました([Addressables](https://docs.unity3d.com/Packages/com.unity.addressables@latest/)、[6.6](https://docs.unity.com/en-us/engine/6000.6/manual/whats-new/unity66))。Godot は meshoptimizer による import 時の自動 LOD、visibility range、occlusion culling を持ちます([Mesh LOD](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html))。Bevy では LOD 専用の section を確認できていません。

slime はここが突出しています。地形は四分木 7 レベル、5,461 タイル、GPU atlas 576 枠で LRU 追い出し、都市は 256m セルで GPU に 96 枠、1 フレーム 4 セルまでの upload です(【コード】`crates/engine/src/terrain/`、`cells.rs`、【実測】)。起動時は gz 約 2MB まで削り、残りは遅延読込して霧の縁で隠します(【文書】`ENGINE_HISTORY.md`)。**汎用エンジンの本体機能で確認できた世界 streaming は Unreal が最も明確で、Godot、Bevy、Flame ではこの水準を本体機能として確認できませんでした**。これは未確認という意味で、不在の断定ではありません。

### Asset pipeline: 制作データを実行時データへ変換する

asset pipeline は Blender などの制作データを実行時向けに変換します。この変換を cook と呼びます。glTF は配布向けの transmission format で、制作用形式ではありません([glTF Spec](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html))。Unreal は FBX、Interchange、glTF、USD に対応し、Incremental Cooking は Beta です([Working with Content](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-content-in-unreal-engine)、[5.8 notes](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-5-8-release-notes))。Godot は取り込み時変換で glTF 2.0 を推奨します([Feature list](https://docs.godotengine.org/en/stable/about/list_of_features.html))。Bevy は 0.20 の `CompressedImageSaver` で BCn / ASTC と mip を出力でき、Assets as Entities は未出荷です([0.20](https://bevy.org/news/bevy-0-20/))。Android の GPU texture 形式は、ASTC が Play デバイスの 80% 超、ETC2 が 95% 超で、Google は ETC2 を既定に推奨します([Android](https://developer.android.com/guide/playcore/asset-delivery/texture-compression))。

slime は glTF を実行時に読まず、実寸化、meshoptimizer の LOD、xatlas の UV 再展開、レイによる焼き直し、impostor(遠景用の板絵)の焼き込み、BC7 / ASTC 圧縮を offline で行います(【文書】`ENGINE_HISTORY.md`、実装は `tools/asset-pipeline/src/`)。tools は約 8.4 千行で、renderer の Rust 行数に迫ります(【実測】)。AI 生成 asset が UV 断片や過剰な三角形を持つことが主な理由です(【文書】)。調査ノートはこの工程をエンジン機能の一部と見なすべきだと推論しており、本調査もこの見方を採ります。

## game loop と entity model では、slime は標準より単純で足りている

### Game loop: 時間を進める枠組み

game loop は毎フレーム「入力 → 更新 → 描画」を回す処理です。実務上の標準形は、固定 dt の simulation に可変レートの描画を組み合わせ、端数を補間する形です([Fix Your Timestep!](https://gafferongames.com/post/fix_your_timestep/))。処理が simulate する時間を超えると遅れが拡大する現象を spiral of death と呼びます。loop の所有者が platform か engine かも設計を左右します([Game Programming Patterns](https://gameprogrammingpatterns.com/game-loop.html))。Defold は input、fixed_update / update / late_update、render の順を文書化しています([lifecycle](https://defold.com/manuals/application-lifecycle/))。Flame は全 component に `update(dt)` と `render(canvas)` を呼びます([game](https://docs.flame-engine.org/latest/flame/game.html))。

**slime は可変 step で、固定タイムステップを持ちません**。dt を 100ms で clamp し、時間スケールでヒットストップとスローを実現します(【コード】`crates/game/src/lib.rs:903-945`)。可変 step は物理とネットワークの再現性を損ないますが、slime にはどちらもありません。ただし iOS は `CADisplayLink` の `targetTimestamp` で animation や physics を駆動するよう求めており、slime の `requestAnimationFrame` 前提はそのままでは使えません([Apple: ProMotion](https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays.md))。

### Entity model: ゲーム内の物の表現

深い継承は機能の組み合わせに耐えず、component による合成が主流になりました([GPP: Component](https://gameprogrammingpatterns.com/component.html))。ECS は entity を ID、component をデータ、system を一括処理の関数に分ける設計です。EC では component 自体が振る舞いを持ちます([ECS FAQ](https://github.com/SanderMertens/ecs-faq)。著者は Flecs の作者で ECS 寄りの立場です)。Unreal は Actor 系に加えて MassEntity を持ち、UE6 では Verse 上の Scene Graph に移る方向です([MassEntity](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-mass-entity-in-unreal-engine)、[GamesBeat](https://gamesbeat.com/unreal-engine-6-will-combine-ue5-and-uefn-into-a-unified-engine-state-of-unreal/))。Unity は GameObject と Entities が併存します([Entities](https://docs.unity3d.com/Packages/com.unity.entities@6.7/manual/index.html))。Godot は Node 木と signal です。Bevy は ECS そのもので、`bevy_ecs` は単体利用が明言されています([README](https://raw.githubusercontent.com/bevyengine/bevy/main/crates/bevy_ecs/README.md))。Flame は component tree で、別実装の ECS である Oxygen は性能がほぼ同等として deprecated になりました([oxygen](https://docs.flame-engine.org/latest/other_modules/oxygen/oxygen.html))。

**slime は ECS も汎用 scene graph も使わず**、種類ごとの具象 struct と `Vec` で済ませています(【コード】`crates/game/src/slime.rs:154-201`)。renderer は `ObjectId` を発行する保持型 API です(【コード】`crates/renderer/src/lib.rs:545-567`)。つまり **ECS は slime 規模の必要条件ではありません**。性能上の利点は大量の同種 entity で現れるという見立ては推論であり、ECS と EC の生産性を比較した信頼できる定量研究は見つかっていません。

### 入力と camera: 操作と視点

入力は端末イベントをゲーム操作へ変換します。Unreal の Enhanced Input は Action、Mapping Context、Modifier を実行時に切り替えられます([Enhanced Input](https://dev.epicgames.com/documentation/en-us/unreal-engine/enhanced-input-in-unreal-engine))。Godot は 4.7 で VirtualJoystick と gyro を追加しました([4.7](https://godotengine.org/releases/4.7/))。Bevy の action mapping は第三者 crate として掲載されていますが、本体の有無は推定です([Bevy Assets](https://bevy.org/assets/))。Flame は mixin を component に付ける方式です([inputs](https://docs.flame-engine.org/latest/flame/inputs/inputs.html))。

camera は視点の制御です。Unity は Cinemachine が 6.6 で core package になり([6.6](https://docs.unity.com/en-us/engine/6000.6/manual/whats-new/unity66))、Bevy は Free、Pan、PanOrbit の controller を持ち([0.18](https://bevy.org/news/bevy-0-18/)、[0.20](https://bevy.org/news/bevy-0-20/))、Flame は `follow` と `setBounds` を持ちます([camera](https://docs.flame-engine.org/latest/flame/camera.html))。Unreal の camera 機能(Spring Arm など)は本調査で未検証です。slime はキーボードとマウスを web-sys で読み、指とゲームパッドはページの JS から wasm に渡します(【コード】`apps/web/index.html:464`、`apps/web/src/lib.rs:549-567`)。camera は肩越し追従、ボス戦の引き、揺れを自前で書いています(【コード】`crates/game/src/lib.rs:1308-1388`)。どの engine の文書からも答えを得られなかった論点が、ゲーム view と周囲の UI の gesture が競合したときの調停です。

## 動きと音の領域は、slime では自前か外部委譲で済む

### Animation: 骨格でキャラクターを動かす

skeletal animation は骨の階層で mesh を変形します。skinning はその頂点変換、blend は複数動作の混合、state machine は動作の遷移管理、IK は末端の目標から関節角を解く手法です。Unreal は IK Rig と Retargeter([IK Rig](https://dev.epicgames.com/documentation/unreal-engine/ik-rig-in-unreal-engine))、Unity は Animator Controller と Blend Tree([Mecanim](https://docs.unity3d.com/6000.6/Documentation/Manual/AnimationOverview.html))、Godot は AnimationTree と 4.6 で刷新された IK を持ちます([AnimationTree](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html)、[4.6](https://godotengine.org/releases/4.6/))。Bevy は clip、player、graph、transition を持ちますが、**IK と state machine は docs top に記載がないという確認に留まり、コードでの不在確認ではありません**([bevy_animation](https://docs.rs/bevy_animation/latest/bevy_animation/))。Flame は sprite が中心で、skeletal は Spine bridge です([flame_spine](https://pub.dev/api/packages/flame_spine))。

slime は TRS 補間、clip サンプリング、root motion を 230 行で自前実装し、GPU skinning は最大 64 関節です(【コード】`crates/engine/src/skeleton.rs`、`crates/renderer/src/dynamic.rs:13`)。速度合成、上半身と下半身の mask、被弾の加算レイヤーを使います(【コード】`crates/game/src/player.rs`、`creature.rs`)。群衆は焼き込みアニメの instance 描画です(【文書】`ENGINE_HISTORY.md`)。**IK とモーフターゲットは使っていません**(【コード】grep)。必要なのは blend と mask までで、editor や retargeting は要件に入りません。

### 物理・衝突: 当たり判定と運動の計算

衝突判定は重なりを検出するだけ、物理エンジンは力、joint、応答まで解きます。Unreal は Chaos、Unity は PhysX と Box2D v3 の低レベル API([Physics](https://docs.unity.com/en-us/engine/6000.3/manual/physics-section/physics-overview)、[6.3](https://docs.unity.com/en-us/engine/6000.3/manual/whats-new/unity63))、Godot は 4.6 から新規 3D project の既定が Jolt です([4.6](https://godotengine.org/releases/4.6/))。Bevy は本体に physics crate がなく、Avian か Rapier を使います([Avian](https://github.com/avianphysics/avian)、[Rapier](https://rapier.rs/docs/))。Flame は「物理エンジンではない」と明言し、tunneling(高速物体のすり抜け)を考慮しないとします([collision](https://docs.flame-engine.org/latest/flame/collision_detection.html))。Defold は Box2D と Bullet([physics](https://defold.com/manuals/physics/))、Cocos は Bullet 約 1.5MB など backend を選べます([Cocos](https://docs.cocos.com/creator/3.8/manual/en/physics/physics-engine.html))。

**slime に物理エンジンはありません**。回転つき箱と円の 2 形状、円柱の押し出し、線分レイキャスト、手書きの重力積分で完結します(【コード】`crates/game/src/world.rs:11-24`、`player.rs`)。戦闘判定は球と縦線分の距離で(【文書】`GAME_DESIGN.md`、実装 `crates/gameplay/src/combat.rs:299`)、車はアーケード式です(【文書】`ENGINE_HISTORY.md`)。必要なのは空間 query と押し出しであり、物理は外部ライブラリを後から足せる領域です。Flame が物理を bridge に分け、Forge2D が Box2D v3 の binding に移ったことはこの判断と整合します([flame_forge2d](https://pub.dev/packages/flame_forge2d))。ただし移行理由の一次記述は確認していません。

### Particle / VFX: 飛沫、光、演出

particle は多数の小片で炎や水を表現する機能です。Unreal の Niagara はモジュール構成です([Niagara](https://dev.epicgames.com/documentation/en-us/unreal-engine/creating-visual-effects-in-niagara-for-unreal-engine))。Unity の VFX Graph は GPU 上のシミュレーションまで扱います([公式](https://docs.unity.com/en-us/engine/6000.6/manual/render-pipelines/choose-a-render-pipeline/pipeline))。機能表の検索要約に「HDRP のみ」と読める記述がありましたが、ノートが要確認としているため根拠にしません。Godot は GPU と CPU の両方を持ちます([Feature list](https://docs.godotengine.org/en/stable/about/list_of_features.html))。Bevy は第三者 crate、Flame は `ParticleSystemComponent` で、CPU か GPU かは文書にありません([particles](https://docs.flame-engine.org/latest/flame/rendering/particles.html))。

slime は CPU シミュレーションと instance 描画で、水滴 384、スプライト 1,280、霧 700、ボス破片 520 などの上限を持ちます(【コード】`crates/renderer/src/slime_body.rs:169-187`、`boss_fx.rs:71`)。魔法陣やきらめきは shader 描画で、flipbook は不採用です(【文書】`GAME_DESIGN.md`)。`effects.rs` が 1,734 行あることも踏まえ、ノートは「データ駆動の VFX より、コードで書きやすい描画 API」が求められるかもしれないと推論しています。

### 音声: 別スレッドで止まらず鳴らす

音声はハードウェアの要求に応じて呼ばれる callback で動き、遅れると音切れになります([Unreal Audio Mixer](https://dev.epicgames.com/documentation/en-us/unreal-engine/audio-mixer-overview-in-unreal-engine))。bus は reverb などを掛ける混合経路です。Godot は bus、effect、2D / 3D 定位を持ちます([Feature list](https://docs.godotengine.org/en/stable/about/list_of_features.html))。Bevy は rodio に依存し、Android は API 26 以上です([Cargo.toml](https://raw.githubusercontent.com/bevyengine/bevy/main/crates/bevy_audio/Cargo.toml)、[examples](https://raw.githubusercontent.com/bevyengine/bevy/main/examples/README.md))。flame_audio は audioplayers の薄い wrapper です([flame_audio](https://pub.dev/packages/flame_audio))。

**slime の Rust 側に音声コードはありません**。ページの Web Audio がマスター、コンプレッサー、畳み込みリバーブ、mp3 の SFX 再生、oscillator の BGM を担います。ゲームは効果音の番号を HUD の JSON に載せるだけです(【コード】`apps/web/index.html:262-292`)。素材は mp3 24 個、524KB で、3D 定位はありません(【実測】、【コード】)。要件自体は軽いものの、native では丸ごと新規に必要です。

### UI / text: HUD と文字

ゲームの UI は HUD、メニュー、text 描画、layout です。Unity 6.3 は runtime に uGUI、editor に UI Toolkit を推奨しつつ、UI 中心の新規 runtime では UI Toolkit も有力とします([比較](https://docs.unity.com/en-us/engine/6000.3/manual/uitoolkits/ui-system-compare))。Godot は Control node 群、bidi text、screen reader 対応を持ちます([Feature list](https://docs.godotengine.org/en/stable/about/list_of_features.html))。Bevy は taffy と parley を使い、0.19 時点の `EditableText` は undo/redo が未対応です([0.19](https://bevy.org/news/bevy-0-19/))。Flame は同じ Flutter tree に overlay を重ねます([overlays](https://docs.flame-engine.org/latest/flame/overlays.html))。Unreal の UMG、Slate は本調査で未検証です。

**slime の HUD は HTML / CSS です**。ゲームが毎フレーム `window.__hud` に JSON を書き、ページが描きます。ダメージ数字やロックオン枠もワールド座標を画面に写した値をページが描きます(【コード】`apps/web/index.html:55,582`、【文書】`GAME_DESIGN.md`)。これは「engine が内部に UI を持たない」実例で、Flame の overlay と同じ委譲の構図です。

## 上位の gameplay 機能は slime の要件にほぼ入らない

scripting はゲームロジックを engine 本体と別の言語で書く層です。Unreal は Blueprint と C++ に加え Verse へ移行中で、Unity は C# を Mono から CoreCLR へ移す途上です([GamesBeat](https://gamesbeat.com/unreal-engine-6-will-combine-ue5-and-uefn-into-a-unified-engine-state-of-unreal/)、[CoreCLR](https://discussions.unity.com/t/coreclr-scripting-and-serialization-update-june-2026/1723299))。Godot は GDScript、C#、GDExtension で、C# は Android / iOS が experimental、Rust の gdext もモバイルは experimental です([gdext](https://github.com/godot-rust/gdext))。Bevy は本体に scripting がなく、`subsecond` で system を実行中に差し替える hot patch を持ちます([0.17](https://bevy.org/news/bevy-0-17/))。slime は Rust のみです。

AI / navigation では、navmesh(歩行可能領域の mesh)と behavior tree(行動の決定木)が標準語彙です。Unreal は Behavior Tree と StateTree を持ちます([Behavior Trees](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-trees-in-unreal-engine)、[State Tree](https://dev.epicgames.com/documentation/en-us/unreal-engine/state-tree-in-unreal-engine))。Godot は navmesh と A* を内蔵し、Bevy は第三者 crate です([Bevy Assets](https://bevy.org/assets/))。slime の敵は発見距離と離脱距離による単純な状態判断で、経路探索はありません。交通は OSM から作ったグラフ上で動きます(【コード】`crates/gameplay/src/ai.rs:1-35`、`crates/engine/src/traffic.rs`)。

networking と save は、slime には**存在しません**。`WebSocket`、`WebRTC`、`localStorage`、`fn save` はいずれも grep でヒットせず、PvP はルールのみです(【コード】`crates/gameplay/src/pvp.rs`)。engine 側では Unreal の Replication と Iris([Networking](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-and-multiplayer-in-unreal-engine))、Unity の Netcode([Manual](https://docs.unity3d.com/Manual/com.unity.netcode.html))、Godot の ENet と RPC があり、save は Unreal の `USaveGame` や Godot の JSON 手順があります([Saving](https://dev.epicgames.com/documentation/en-us/unreal-engine/saving-and-loading-your-game-in-unreal-engine)、[Saving games](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html))。要件を「slime と同規模」と字義どおりに読めば不要です。ただし出荷するゲームに save が要らないとは限らず、ここは要件側で別に判断すべきです。

## 差が開くのは editor とモバイル運用、host への組み込み

### Editor / tools: 作る人のための機能

Unity と Unreal は editor、profiler、frame debugger を統合しています([Unity 6.3](https://docs.unity.com/en-us/engine/6000.3/manual/whats-new/unity63))。Godot も debugger、visual profiler、remote inspector を持ちます([Feature list](https://docs.godotengine.org/en/stable/about/list_of_features.html))。**Bevy は「baseline editor を upstream に入れられなかった」と自ら認め**、最優先に位置づけています([Sixth Birthday](https://bevy.org/news/bevys-sixth-birthday/))。Fyrox 1.0 は Rust 製で editor を持ちますが、「production-ready」は自己申告で採用事例は未確認です([Fyrox](https://fyrox.rs/blog/post/fyrox-game-engine-1-0-0/))。

slime に editor はなく、**それでも成立しています**。代わりに GPU pass の `timestamp-query` 計測、URL パラメータ、フリーカメラ、オートパイロット、シェーダー失敗行の二分探索、テスト 106 件があります(【コード】`crates/renderer/src/profiler.rs`、`autopilot.rs`、【実測】)。一方で、タイルベース GPU ではパス時間の合計が実際より大きく出る、Mac は GPU クロック低下で比較が揺れるなど、計測そのものの難しさが記録されています(【文書】`ENGINE_HISTORY.md`)。Editor なしは code-first として成立しますが、その場合は外部ツールと import の品質に依存します(本調査の判断)。

### Platform とモバイル: 持続性能と OS の割り込み

モバイル engine の設計目標はピークではなく持続性能です。Android の Thermal API は発熱余地を予測し、早めの品質低下を勧めます([Thermal](https://developer.android.com/games/optimize/adpf/thermal))。iOS はメモリ上限を超えると終了させ([Apple](https://developer.apple.com/documentation/xcode/reducing-your-app-s-memory-use.md))、背景アプリの GPU 利用を制限します([Metal background](https://developer.apple.com/documentation/metal/preparing-your-metal-app-to-run-in-the-background.md))。Android では surface が背景化で破棄されえます([SDL の修正記録](https://discourse.libsdl.org/t/sdl-gpu-vulkan-handle-vk-error-surface-lost-khr-in-acquire-path/67125)。公式文書ではありません)。Android の Swappy はフレーム間隔のむら(frame pacing)を解決します([Frame Pacing](https://developer.android.com/games/sdk/frame-pacing))。Vulkan はアクティブ Android 端末の 85% が対応します([Vulkan](https://developer.android.com/games/develop/vulkan/overview))。wgpu では Vulkan と Metal が first-class、GLES は best-effort です([wgpu](https://docs.rs/wgpu/latest/wgpu/))。slime の GLES 除外をそのまま native に適用すると、残り約 15% は対象外になります(導出)。

**slime はブラウザ経由のみで、iOS / Android の native アプリはありません**(【実測】`apps/`)。iOS 実機の確認手順は未着手で、各節に「Safari では未計測」とあります(【文書】`ENGINE_HISTORY.md`)。Pixel 10 の PowerVR で外壁パイプラインが生成できず簡易外壁へ切り替えた記録は(【コード】`gbuffer.wgsl:30`、【文書】`CLAUDE.md`)、ドライバー差が実在することを示します。**fps、メモリ、発熱の数値はリポジトリに残っていません**。さらに、ブラウザから無償で得ている Web Audio、DOM、fetch、DecompressionStream、Gamepad API は、native では代替が必要です。slime のコードに現れない要件で、棚卸しで最も見落としやすい点です(ノートの推論)。

ランタイムサイズの比較は信頼度が低く、桁の参考に留まります。Unity は iOS 空プロジェクトで約 20MB、最適化で 12MB 未満が公式値です([Unity](https://docs.unity3d.com/Manual/iphone-playerSizeOptimization.html))。Unreal の数値は版の揃わないフォーラムの逸話のみで、UE 5.8 の値はありません。Godot と Bevy も逸話のみです。Defold は Android 2.56MB、iOS 1.35MB を掲げますが、**競合比較を含む自社ページで、同じページ内に別の値もあり矛盾しています**([Defold](https://defold.com/gamescom2025/))。正確な比較には自前の build が必要です。

### Host への組み込み: 最も製品差が大きい

組み込みの難しさは、engine が process と window をどれだけ所有するかで決まります。**Unity as a Library は Android / iOS で full-screen のみ、複数 instance 不可、unload 後も 80〜180MB を保持します**(Industry 顧客は異なる場合あり。[Unity](https://docs.unity.com/en-us/engine/6000.3/manual/platform-specific/cross-platform-features/unityasa-library))。LibGodot は host が `iteration()` で 1 フレームずつ駆動する API ですが([PR #90510](https://github.com/godotengine/godot/pull/90510))、2026-03 時点で host の既存 surface を渡す標準手段がなく、upstream は途上です([proposal](https://github.com/godotengine/godot-proposals/issues/14435))。Bevy は community の `bevy-in-app` が winit を外し任意サイズの view で動かしますが、対応は Bevy 0.18 までです([GitHub](https://github.com/jinleili/bevy-in-app))。Flame の `GameWidget` は普通の widget で、SpriteKit と RealityKit も `SpriteView` と `RealityView` で view として組み込めます([overlays](https://docs.flame-engine.org/latest/flame/overlays.html)、[SpriteView](https://developer.apple.com/tutorials/data/documentation/spritekit/spriteview.json)、[WWDC25](https://developer.apple.com/videos/play/wwdc2025/288/))。合成方式は 2 つあります。engine が独立 surface を占有して UI を重ねる方式では z-order や同期のずれが出やすく、同じ compositor で合成する方式ではこの問題を避けられます(この対比は調査者の整理です)。

## Whisker への示唆(いずれも仮説)

ここから先は検証済みの結論ではなく、Whisker の実装とも突き合わせていない仮説です。設計案も提示しません。

仮説 1 は優先順位です。slime 規模が問うのは物理の有無より 3D 描画、streaming、offline の asset 変換であり、「L2 最小エンジン」を揃えただけでは要件を満たしません。仮説 2 は委譲です。Flame が Flutter に任せるように、HUD、text、入力の一部は Whisker の UI 層が担える可能性があります。ただし slime の毎フレーム JSON に相当する更新を UI 層が負荷なく受けられるかは未検証です。音声には既存基盤の流用先が見えず、新規に必要になると見込みます。仮説 3 は「買う」領域です。物理、音声デコードは外部 crate で埋める余地があり、Bevy の例はその代償として本体の破壊的変更に追従する負担を示します。仮説 4 は組み込みです。Whisker の描画基盤に Flutter GPU 相当の texture 受け渡しがあるかは未確認で、なければ独立 surface 型が候補になり、z-order、gesture 調停、surface 再生成が論点になります。仮説 5 は検証順です。機能の選定より先に、slime 相当の負荷をモバイル実機で測らなければ、規模の要件自体が達成可能か判断できません。

## 結論

「ゲームエンジンの機能」を網羅表として眺めると全領域が必要に見えますが、slime を当てると様相が変わります。Rust 約 2.8 万行のランタイムは、editor、物理エンジン、ECS を持たないまま 8km 四方の世界を描きます。エンジンの必須機能は固定されたリストではなく、ゲームが何に負荷をかけるかで決まります。Flame から学ぶべきは下限の機能一覧より、host に任せる範囲の線引きです。

未解決の核心はモバイルです。Unreal、Unity、Godot はいずれも高機能描画をモバイルで制限または別 tier にしており、slime の画質セットがその内側に収まる根拠はありません。開発記録の短さ(`ENGINE_HISTORY.md` の日付で約 11 日)も、人時の記録がなく AI エージェントの関与度も不明なため、工数の根拠にはなりません。また Unreal は UE6、Unity は CoreCLR、Flame は 2.0 への移行期にあり、本表は 2026-10 時点のスナップショットです。
